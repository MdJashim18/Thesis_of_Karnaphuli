# Day 22: End-to-End HTTP API Pipeline Test Log

## 1. Objective

To test the end-to-end sensor telemetry pipeline for the Karnaphuli Tunnel Structural Health Monitoring (SHM) prototype using ESP32, a Python HTTP API, InfluxDB, and the InfluxDB dashboard.

The test focuses on sensor data generation, HTTP communication, database storage, dashboard visualization, and identifying any incomplete telemetry fields or communication issues.

## 2. Project Information

- **Project:** Karnaphuli Tunnel Structural Health Monitoring (SHM)
- **Device:** ESP32 DOIT DEVKIT V1
- **Device ID:** `ESP32-GW-LAB-001`
- **Gateway ID:** `gateway01`
- **Zone ID:** `LAB_PROTOTYPE`
- **Communication protocol:** HTTP POST
- **API endpoint:** `http://192.168.0.102:5000/telemetry`
- **Database:** InfluxDB OSS 2.9.1
- **InfluxDB bucket:** `tunnel_telemetry`
- **Measurement:** `tunnel_telemetry`
- **Dashboard:** InfluxDB UI at `http://localhost:8086`

## 3. Hardware and Sensors

| Component | Purpose | ESP32 connection |
|---|---|---|
| ESP32 DOIT DEVKIT V1 | Main controller and telemetry sender | — |
| DHT22 | Temperature and humidity measurement | GPIO 4 |
| MPU6050 | Acceleration and angular velocity measurement | SDA: GPIO 21, SCL: GPIO 22 |
| HW-038 water sensor | Water-level-related analog readings | AO: GPIO 34 |
| HX711 with load cell | Load-cell signal acquisition | DT: GPIO 18, SCK: GPIO 19 |

**Calibration note:** The load-cell calibration has not been reliably validated. Therefore, `load_kg` is currently a placeholder and must not be interpreted as a verified physical weight.

## 4. Software and Pipeline Architecture

The tested data flow is:

`Sensors → ESP32 → HTTP POST → Python Flask API → InfluxDB → Dashboard`

The ESP32 collects sensor readings and packages them into a JSON payload. It sends the payload to the Flask API through an HTTP POST request. The API is responsible for processing the received telemetry and storing the appropriate fields in InfluxDB.

The InfluxDB dashboard is then used to inspect the stored sensor data.

**Note:** This Day 22 test uses the HTTP API pipeline. MQTT/Mosquitto is not the communication path being evaluated in this test.

## 5. Test Procedure

1. Start the Python Flask HTTP API server.
2. Start InfluxDB and ensure that the `tunnel_telemetry` bucket is available.
3. Confirm that the ESP32 and computer are connected to a network that allows communication with the API.
4. Power on the ESP32 and open the Serial Monitor at the configured baud rate of 115200.
5. Observe the sensor readings and the JSON payload generated by the ESP32.
6. Check the HTTP response status and any communication errors printed in the Serial Monitor.
7. Open the InfluxDB dashboard and inspect the recent telemetry records.
8. Change the water sensor's exposure to water and observe whether its raw reading changes.
9. Check which expected fields are visible in the stored telemetry.
10. Record any errors and any fields that still require verification.

## 6. ESP32 Serial Monitor Observations

During the test, the following output was observed:

```text
Load raw: 444
Load kg: 0.000 (placeholder)
Quality: partial
HTTP status: -11
HTTP error: read Timeout
```

The ESP32 generated the following JSON payload:

```json
{
  "device_id": "ESP32-GW-LAB-001",
  "gateway_id": "gateway01",
  "zone_id": "LAB_PROTOTYPE",
  "temperature": 29.70,
  "humidity": 85.50,
  "accel_x": 0.220,
  "accel_y": -0.019,
  "accel_z": 10.872,
  "water_raw": 1131,
  "load_raw": 444,
  "load_kg": 0.000,
  "dht_valid": true,
  "mpu_valid": true,
  "hx711_valid": true,
  "quality_flag": "partial"
}
```

### Interpretation

- The ESP32 generated a telemetry payload containing the device identifiers and sensor fields.
- Temperature, humidity, acceleration, water sensor, and load-cell-related values were included in the payload.
- `load_raw` represents the raw load-cell reading, while `load_kg` remains an uncalibrated placeholder.
- HTTP status `-11` accompanied by `read Timeout` indicates that the ESP32 HTTP client timed out while waiting for a response. It does not, by itself, prove whether the API stored or failed to store that particular request.
- The `quality_flag` value was observed as `partial`; the criteria used to assign this flag should be checked against the firmware's validation logic.

## 8. Water Sensor Verification

The water sensor was exposed to water during testing. Its raw reading changed in the ESP32 Serial Monitor, and the `water_raw` field was subsequently visible in the InfluxDB dashboard/query results.

This provides evidence that the water sensor reading was being generated and that water-related telemetry was available in the database.

The raw analog value is a sensor reading, not a calibrated water depth in centimetres. A separate calibration and validation procedure would be required to estimate physical water depth reliably.

## 9. Load-Cell Field Verification

The ESP32 payload included:

- `load_raw`: the raw HX711/load-cell reading
- `load_kg`: the placeholder value `0.000`

The `load_raw` field was not yet confirmed as visible in the InfluxDB results during this test.

The presence of `load_raw` in the ESP32 JSON payload does not guarantee that the Flask API writes it to InfluxDB. The API's field-mapping and database-write logic must be checked if the field remains absent.

The `load_kg` value must remain documented as a placeholder until calibration and independent validation are successful.

## 10. HTTP Timeout Observation

**Observed issue:** The ESP32 reported `HTTP status: -11` and `read Timeout` during at least one request.

This means that the HTTP client did not receive the expected response within its configured waiting period. The database may still contain records from other requests, so dashboard data and a timeout can coexist.

Recommended follow-up checks:

1. Confirm that the Flask API remains running and reachable.
2. Inspect the Flask terminal output for incoming requests, exceptions, and InfluxDB write errors.
3. Check whether the API response is delayed by database writes or other processing.
4. Verify the HTTP client's timeout setting and request interval.
5. Compare request timestamps with InfluxDB record timestamps to determine whether the affected request was stored.
6. Repeat the test and record successful responses, timeout counts, and missing records.

Do not mark HTTP communication as fully reliable until repeated tests support that conclusion.

## 12. Limitations

- The HTTP timeout has not yet been fully diagnosed.
- The exact timed-out request has not been confirmed as successfully stored or lost.
- The `load_raw` field still requires verification in InfluxDB.
- The `load_kg` field is not a calibrated measurement.
- The water sensor's raw reading has not been converted into a validated physical water-depth measurement.
- Dashboard records with different timestamps and values must not be treated as proof that every ESP32 request was successfully stored.

## 13. Conclusion

The Day 22 end-to-end HTTP API pipeline test demonstrated that the ESP32 generated sensor telemetry, records were visible in InfluxDB, and the water sensor's changing raw reading was available for monitoring.

However, an HTTP read timeout (`HTTP status: -11`) occurred during testing. The storage status of the specific timed-out request remains unconfirmed. The `load_raw` field also requires verification, and `load_kg` remains a placeholder because reliable calibration has not been established.

**Overall status: PARTIAL — telemetry generation and database visualization observed; HTTP reliability and complete load-field storage still require verification.**

The next step is to inspect the Flask API's field-mapping and write logic, verify `load_raw` in InfluxDB, and repeat the end-to-end test to evaluate HTTP response reliability.
